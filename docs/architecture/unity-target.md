# Unity UI Toolkit pilot

`UNITY-INTERACTIVE-COMPONENTS-01` adds a registered Unity generation target with a bounded component allowlist and a local UPM package. Read [the package README](../../packages/ds-unity/README.md) for installation, supported behavior, commands and limitations.

The lowering path is `ComponentIR → anatomy walker → C# UXML elements → attached runtime behaviors`. The walker ([`walker.ts`](../../packages/ds-codegen/src/frameworks/unity/walker.ts)) lowers `ir.dom`, or a tree synthesized from `ir.parts` when a contract declares no `dom`, into one generated `VisualElement` class per component and one per `ir.compoundParts` entry. The behavior dispatcher ([`behaviors.ts`](../../packages/ds-codegen/src/frameworks/unity/behaviors.ts)) selects which runtime behavior the generated constructor attaches: a boolean form-control fact selects `BooleanControl`, a single `select`/`toggle-item` interaction trigger with hidden presence selects `ItemGroup`, and a part-anchored, non-blocking, click-open surface selects `AnchoredSurface`. Unsupported shapes throw. No rule branches on component, part, channel or class identity; the one name table is the item-group option vocabulary (`type`, `collapsible`, `orientation`, `activationMode`, `loop`, `appearance`, `unmountInactive`), applied only when `ItemGroup` was selected by fact. [`lore.test.ts`](../../packages/ds-codegen/src/frameworks/unity/lore.test.ts) scans the emitter for predicates against lowercase part, channel and prop literals and admits only that table. See [Anatomy walker](#anatomy-walker) for the rules.

The runtime behaviors are plain C# classes, not `VisualElement` subclasses; `packages/ds-unity/Runtime` carries no hand-written element type. They own Unity event delivery, selection and focus state, dismissal and panel coordinates, and discover the composed sub-elements they pair by part class under their host. They do not read JSON contracts at runtime.

Verification has separate boundaries: TypeScript tests check routing and contract influence; compiler-only checks use real Unity reference assemblies and the UXML generator; EditMode tests require an activated Unity Editor and exercise import plus live panel events. The existing `governed:rail` does not execute the Unity lane. Neither compilation nor narrow EditMode facts establish full styling, accessibility or player runtime parity.

Unity's [custom-control documentation](https://docs.unity3d.com/6000.0/Documentation/Manual/UIE-create-custom-controls.html) defines the partial-class / `UxmlElement` registration mechanism. Unity's [package layout documentation](https://docs.unity3d.com/6000.0/Documentation/Manual/cus-layout.html) defines Runtime, Editor, Tests and Samples packaging.

## Recorded pilot verification

At source commit `c3b29662`, Unity 6000.5.3f1 ran `node scripts/unity-tests.mjs` with graphics enabled: all 14 EditMode cases passed, with no skipped cases. The runner imported the package as an embedded UPM package and imported its UXML/runtime sample into a consuming project's Assets directory. The UXML witness constructs the generated controls, discovers compound items, activates a tab and opens the popover. Other cases exercise boolean state, controlled requests, accordion single/multiple selection, keyboard tab navigation, panel retention, anchored dismissal and geometry.

The initial graphics-disabled run failed during panel setup; it supplied no behavior evidence. The first graphics-enabled run exposed a test-policy overlap: outside pointer focus changes also trigger blur. The final pointer case disables blur to isolate the outside-pointer policy; a separate real-focus case verifies blur across the anchor/content boundary.

The local evidence files are `tmp/unity-pilot/results.xml` and `tmp/unity-pilot/editor.log`, reproduced by the command above. They are not committed build artifacts. The existing root/framework suites and admission rail also passed during the slice; those checks do not extend Unity's narrow runtime claim. Player builds, screen-reader behavior and full visual parity remain outside this pilot.

## Styling projection

The package stylesheet `packages/ds-unity/Runtime/Resources/FullStackDS/Controls.uss` is generated, not authored. [`uss.ts`](../../packages/ds-codegen/src/frameworks/unity/uss.ts) runs through the `emitTargetAssets` seam of the codegen CLI after a full-corpus Unity run and writes two assets: the stylesheet and the unsupported ledger `Controls.unsupported.json` beside it. The CLI records only rail targets in the emission manifest, so these assets stay outside it until P5 admission.

The sheet has two sections. The token section declares every consumed `--fsds-*` custom property from `resolved.tokens.json` on `.fsds-theme`, overrides it on `.fsds-theme.fsds-theme--dark`, and layers each brand from the token build's brand layer on `.fsds-theme.fsds-brand-<brand>` in both themes. The component section lowers `ir.nativeStyleRules`, the same framework-neutral style facts the GPUI target reads, into one USS rule per part, variant, state and pseudo predicate. State predicates land on the runtime's state classes (`is-checked`, `is-disabled`, `is-hover`, `is-active`, `is-focus`) at the host the behavior sets them on; variant predicates land on the `<prefix>--<value>` recipe classes; floating content restates its component scope because it leaves the component's subtree; a composed-content host repeats its owner's container facts so composed children lay out as the contract describes.

USS is a subset of CSS, and the projection lowers rather than copies. Logical sides become physical LTR sides, `inline-flex` becomes `flex` with a row direction, `outline` becomes a focus-only border, `gap` becomes the `--fsds-gap` custom property that the runtime's `Gap` helper realizes as child margins (a ScrollView's in-flow children live in its content container, which does not inherit the host's custom properties, so `Gap` resolves that container itself). A declaration with more than one component never carries `var()`: USS keeps only the variable and silently drops the other components, so scope-invariant tokens are inlined and scope-varying ones are ledgered. Everything the projection cannot express is written to the ledger with a reason (`uss-property`, `uss-scalar`, `uss-pseudo`, `uss-pseudo-element`, `uss-selector`, `uss-owner-mismatch`, `uss-floating-scope`, `uss-design-slot`, `uss-var-composite`) instead of being approximated. The support boundary classifies the token and style sidecar leaves these rules consume as `lowered` and the ledgered families as `refused` or `pending`; the emitter never reads the boundary.

The runtime selects scopes rather than values: behaviors attach the sheet without adding `fsds-theme`, consumers call `Theme.SetDark` and `Theme.SetBrand` on an ancestor, and floating content mirrors its owner's theme classes. `Samples~/InteractiveControls/Sample.uss` carries sample-only skin for Unity's built-in controls at the lowest specificity; it is not package styling.

Witnesses: `uss.test.ts` pins the projection on synthetic contracts outside the corpus, including the composite rule, the focus and display lowering, the floating restatement and the brand carry-over; `cli.test.ts` pins the seam. `audit:token-resolvability` and `audit:variant-realization` each scan the generated sheet as a `unity` surface. In the package, `StylingTests.cs` asserts the stylesheet imports with no errors or warnings, resolves token values in light and dark scope, checks Switch geometry at every size including the thumb's translate, and renders Player panels at 640×800 and 320×600 into screenshot witnesses beside the runner logs; `GapTests.cs` pins the gap realization including the ScrollView case. These bounded checks do not establish arbitrary-resolution visual parity, brand design-slot overrides (ledgered as `uss-design-slot`), the Accordion chevron glyph (a `componentRef` placeholder until P4), or the a11y-attribute and web-template state selectors (`[aria-expanded]`, `tab--active`), which stay ledgered as `uss-selector` until the IR carries them as state facts.

## Anatomy walker

`UNITY-ANATOMY-WALKER-01` replaces the per-shape wrapper emission with a generic walk. The rules, each read from IR facts:

- **Classes.** The component root is `[UxmlElement] public partial class <Name> : VisualElement`, plus `INotifyValueChanged<bool>` when the selected channel is boolean. Each `ir.compoundParts` entry becomes `<Name><Part>` with a base chosen by fact: `Button` for a trigger part (the form-control part, an interaction trigger or the surface anchor) or a `button` tag, `ScrollView` for interactive surface content, otherwise `VisualElement`. Compound nodes emit nothing inline in their parent; the consumer composes them, as on the web.
- **Part identity.** Every rendered part sets `name = "<part>"`; the root carries the `cssPrefix` class and every other part `<cssPrefix>__<part>`. Non-compound parts inside a class are public read-only element properties in document order; a trigger part is a `Button`, a text leaf with literal content a `Label`, anything else a `VisualElement`. A `componentRef` node is an identity-only placeholder until P4.
- **Insertion points.** A `children` hole that is its parent's only child makes that parent the `contentContainer`. Otherwise a private `children` host (class `<cssPrefix>__children`) sits at the hole's position and becomes the container. The same host is inserted at the first compound node's position when rendered siblings follow it, so composed sub-elements keep document order. A named slot becomes a public `<Slot>Slot` host. More than one hole, iteration and conditional guards other than the content-presence guard throw `UNITY_UNSUPPORTED_ANATOMY`.
- **Props.** Channel members become the channel API (`ChannelName`, `ChangeHandler`; boolean: the value attribute, `value`, `SetValueWithoutNotify`, `RequestValue`, `Controlled`, `ValueRequested`; string: `Value`, `Values`, `Controlled`, `ValueRequested`, `ValueChanged`). The interaction's `disabledProp`, or a `disabled=prop:*` binding on the form-control part, becomes `Disabled`. A variant axis the attached behavior consumes (an item-group vocabulary entry, or the surface placement prop) becomes a validated string attribute that swaps the root modifier class `<cssPrefix>--<value>` (the web class recipe) through the runtime `Variants` helper and drives the behavior knob; every other axis (Switch `size`) is a styling axis, emitted as the same validated attribute and modifier class when the generated stylesheet carries a rule keyed on that modifier, and withheld when no behavior knob and no stylesheet rule consumes it. Dismissal `enabledBy` props and the placement prop come from `normalizedDismissalTriggers` and `surface.positioning`. Trigger sub-elements get `Disabled`; the ItemGroup trigger and content sub-elements get `Value` and implement `IKeyedPart`, the pairing key.
- **Behavior attachment.** After the tree is built the constructor calls `BooleanControl.Attach`, `ItemGroup.Attach` or `AnchoredSurface.Attach` with options read from the IR: the control part and a `labelHost` when the root tag is `label` (a click on the label toggles the control once), trigger and content part classes, the operation, `multiple` from the channel type, focus strategy, orientation and wrap, and the state class. The state class is `is-<value>` for the non-initial value of the first `effect: channel` state dimension, else the selection dimension: `is-checked`, `is-selected`, `is-open`.
- **Geometry.** Generated C# sets no inline geometry; every size, padding and gap fact reaches the element through the generated stylesheet (see [Styling projection](#styling-projection)), so a consumer's USS can override it.

Consumer composition follows the contract's compound parts rather than runtime-invented item types: `<ds:Accordion><ds:AccordionItem><ds:AccordionHeader><ds:AccordionTrigger value="a" text="A"/></ds:AccordionHeader><ds:AccordionContent value="a">…</ds:AccordionContent></ds:AccordionItem></ds:Accordion>`, `<ds:Tabs><ds:TabsList><ds:TabsTab value="a" text="A"/></ds:TabsList><ds:TabsPanel value="a">…</ds:TabsPanel></ds:Tabs>`, `<ds:Popover><ds:PopoverTrigger text="Help"/><ds:PopoverContent>…</ds:PopoverContent></ds:Popover>`, and a Switch's label is its children. Behaviors discover composed parts on panel attach, on layout change, before pointer or submit input reaches a trigger, and on public API calls; a part inserted into an already attached root shows its state at the next of those events, or immediately after `Group.Synchronize()`.

[`factory.test.ts`](../../packages/ds-codegen/src/frameworks/unity/factory.test.ts) drives the walker with synthetic contracts outside the corpus (different part names, a named slot, a hole with siblings, composed content followed by a rendered sibling, a parts-only shape, knob-driven and withheld variant axes) so the output is shown to be rule-derived rather than corpus-shaped. The walker does not consult the support boundary; the boundary describes the walker and `assertRealized` checks the two agree.

## Capability inventory and standalone boundary

`UNITY-CAPABILITY-PLAYER-01` introduces reproducible source accounting:

```sh
pnpm --filter @full-stack-ds/codegen build
node packages/ds-codegen/dist/frameworks/unity/capabilities.js > tmp/unity-capabilities.json
node scripts/unity-player.mjs
```

The inventory walks the authoritative contract loader and registry. Each component receives a lowering `status`; each normalized prop is classified as `emitted-api` or `not-emitted` and carries the support-boundary rule for its family. Every contract and token/style sidecar leaf is listed individually with the disposition (`lowered`, `pending` or `refused`) and rule id that the [support boundary](#support-boundary) assigns it. Contract/sidecar hashes bind the observations to their inputs. The inventory is accounting, not proof of semantic parity; the generation gate belongs to the support boundary. `not-emitted` means no matching generated C# property: a callback can be lowered through a shared-runtime C# adaptation and a default channel through imperative initial assignment, and the boundary records each such adaptation as an explicit `via` mechanism rather than crediting it from property names.

The inventory finds only the allowlist admitted. Checkbox and ToggleSwitch pass the shape dispatcher but are unadmitted candidates; that does not establish their intended anatomy or behavior. Most other corpus shapes are rejected as `unsupported-shape`. The pilot emits no generated C# property for default channels, callback props, form fields, or Tabs idBase; Switch `size` is emitted because the generated stylesheet carries its modifier rules. The boundary records the channel defaults and callbacks as `lowered` through runtime adaptations, Switch `name`/`value` and Tabs `idBase` as `refused` DOM-only fields, and the styling axes as `lowered` through the stylesheet projection. An unknown prop on an allowlisted contract is listed as `not-emitted` in the inventory and fails generation until the boundary adjudicates its family.

The standalone witness copies the package into a fresh consuming project, creates a scene and PanelSettings, builds a macOS app, launches its executable with graphics, and requires an exact run identity and ordered check set. It records source hashes, logs, JSON and a screenshot under `tmp/unity-player/<run-id>/`. Tests prove package resources, generated UXML types, selected state changes, single callback delivery and popover placement/dismissal in an actual OSXPlayer process. UI events are synthetic. It does not prove physical keyboard/controller input routing, accessibility, UI Builder save/reopen, minimum-version compatibility, other operating systems or IL2CPP. The fixture runs in the background so an unattended window cannot stall the measurement.

At source `18abc116`, fresh run `9e7113e5-da40-4802-9e9b-8b8c0df36f90` passed all 11 required standalone checks; the optional Editor lane also passed all 17 cases. Recorded environment: Unity 6000.5.3f1, macOS, Metal, standalone Player. The package's declared 6000.0 minimum remains unverified; do not interpret this newer-version witness as minimum-version admission. The first background-disabled launch produced no usable receipt. A subsequent default-template project passed, but the stricter minimal project exposed an undeclared Test Framework dependency: package Editor tests were compiling without NUnit. The test assembly uses a package-version define constraint, so consumers without the Test Framework do not compile the optional tests; the explicit Editor test lane still exercises them. The minimal manifest declares only UIElements plus screenshot/image-conversion modules needed by the witness.

## Support boundary

`UNITY-SUPPORT-BOUNDARY-01` commits the machine-readable statement of what the Unity target lowers, defers and refuses: [`support-boundary.json`](../../packages/ds-codegen/src/frameworks/unity/support-boundary.json), validated against [`support-boundary.schema.json`](../../packages/ds-codegen/src/frameworks/unity/support-boundary.schema.json) and evaluated by [`boundary.ts`](../../packages/ds-codegen/src/frameworks/unity/boundary.ts). The file is an ordered rule list; the first matching rule wins. Every contract leaf and every token and style sidecar leaf resolves to exactly one rule, and each rule carries one disposition:

- `lowered`: the Unity emitter or the shared C# runtime realises the family. `via` names the mechanism, such as `RegisterValueChangedCallback` for a boolean channel's change member or pre-attachment assignment for a channel default.
- `pending`: a later parity phase lowers the family. `phase` names it and `reason` states what is missing. The phases are P2 (generic anatomy walker), P3 (styling projection), P4 (interaction families) and P5 (corpus and admission); the file's `phases` block summarises each.
- `refused`: UI Toolkit cannot realise the family idiomatically, and `reason` states why. Examples: HTML form submission fields have no form element to serialise into, USS has no `@keyframes`, and ARIA roles and relationships have no assistive-technology consumer.

The validator rejects a `lowered` rule without `via`, a `pending` rule without a phase and reason, and a `refused` rule without a reason. Only `pending` rules may be catch-alls.

Leaves are identity-keyed JSON pointers. An array element that carries a `name` or `part` is keyed by that identity rather than by its index. A prop member is keyed `<role>:<name>`, where the role comes from the contract's own `channels` and `form` blocks: `channel-value`, `channel-default`, `channel-change`, `form-field`, or `plain` for every other prop. Tabs' `value` is therefore keyed `channel-value:value`, while Switch's `name` and `value` are form fields because Switch participates in forms. Rules classify pointer families and never name a component. A `lowered` disposition says the family has a lowering; the component's inventory `status` says whether the dispatcher applies it to that component.

### Generation gate

The Unity emitter implements the codegen `admitContract` hook. The CLI's generate path calls it once per component with the validated contract, sidecar tokens and styles merged, before any lowering; watch mode passes the bare contract without the sidecar merge. A refusal fails generation like an emitter error, including under `--dry-run`. The gate has two refusals:

- `UNITY_BOUNDARY_UNCLASSIFIED`: a leaf matches no rule. Generation fails for every component, allowlisted or not.
- `UNITY_BOUNDARY_UNADJUDICATED`: an allowlisted component carries a leaf that only a `catchAll` rule matches. Catch-all rules classify unknown families as `pending` so that nothing is silently supported, and an allowlisted component may not rest on one. Widening the allowlist, or adding a prop to an admitted contract, therefore fails generation until a family rule in the boundary file decides it.
- `UNITY_BOUNDARY_UNREALIZED`: a `lowered` rule that declares `realizes` does not hold for the control this component gets. `emitted-property` requires the prop to be a generated public property, `selected-channel` and `selected-channel-member` tie channels and their props to the one channel the dispatcher selected, and `channel-change-event` requires an event to be emitted through that channel's change prop. A prop whose name belongs to a lowered family of another base (`orientation` on a Switch), a second channel, or an unrelated event is refused rather than dropped.

The dispatcher refuses by fact what a runtime behavior would otherwise contradict: a focus strategy that does not match the behavior (`UNITY_UNSUPPORTED_FOCUS`), a portal on a non-surface shape (`UNITY_UNSUPPORTED_PORTAL`), a surface whose portal is disabled, whose presence is not persistent, whose content is not interactive, whose interaction presence is not unmount, or whose dismissal trigger has no `CloseOn*` knob (`UNITY_UNSUPPORTED_SURFACE`), and a state model with no single projectable value (`UNITY_UNSUPPORTED_STATE`). Those refusals are what allow the matching families to be classified `lowered`.

An explicit `generate <Name>` request that bypasses the allowlist tolerates catch-all leaves but not unclassified or unrealised ones. The hook is admission only: it builds the IR to check realisation and derives no emitted source, so the generated C# does not depend on the boundary.

### Audit

`pnpm run audit:unity-boundary` builds the codegen package and runs the capability inventory in `--check` mode over the whole corpus. It fails on any unclassified leaf, on any allowlisted component that relies on a catch-all rule, on any dead rule that matches no live leaf, and on any allowlisted component whose control does not realise a lowered claim. It prints leaf counts per disposition and pending counts per phase. [`boundary.test.ts`](../../packages/ds-codegen/src/frameworks/unity/boundary.test.ts) pins the same audit, so the root `pnpm test` run in CI enforces it. The tests also pin role derivation from `channels` and `form`, identity keying, first-match ordering, `valueIn` filtering, both refusal codes and rejection of malformed rule files.

### What the boundary does not prove

The boundary is accounting plus a gate. A `lowered` disposition records that a family has a lowering; it is not semantic or runtime proof that the lowering is correct, and behavior evidence comes from the EditMode and Player witnesses above. Refusals are revisable decisions about UI Toolkit, not permanent exclusions. The `a11y` refusal, for example, holds only while UI Toolkit populates no assistive-technology tree, and the rule names that integration as the trigger to revisit it. Unity remains outside the TypeScript admission rail, and its EditMode and Player lanes are local runs, not CI gates.

### Next dependencies

In order. Each phase retires its `pending` rules, and the audit's per-phase pending count measures what remains.

1. **IR state facts.** Promote `isCompound` and `isRootOnly` from name lists to role-derived facts, and promote the a11y-attribute and web-template state selectors the native style grammar refuses (`[aria-expanded="true"]`, `tab--active`) to a `state` predicate derived from `states.dimensions`, so the Accordion chevron rotate and the selected-tab styling leave the `uss-selector` ledger.
2. **P4, interaction families.** Lower static pressables, blocking and hover surfaces, composite and non-boolean form controls, month date grids, componentRef composition (the walker's placeholder nodes, including the Icon glyph the Accordion chevron needs), iteration and conditional guards, messages, motion and typed C# declarations. Each family moves from a catch-all to an explicit `lowered` or `refused` rule.
3. **P5, corpus and admission.** Compose an independent settings/inventory workflow to select the next component families and widen the allowlist toward the SwiftUI set, then add a CI compile lane, a committed-byte drift diff and build/runtime admission. Before widening platform promises, verify actual input routing, accessibility feasibility, UI Builder round trips and the minimum Unity version. The standalone fixture consumes the package sample, so it is not that independent application acceptance test.
