# Current Implementation Snapshot

This is the routing document for current project state. Read it before older architecture notes, ADRs, and successor-work docs when deciding whether a surface is doctrine, partial machinery, or proven machinery.

**How to read this document's freshness.** Two different things carry evidence here, and conflating them is how this header went stale before:

1. **Last full-sweep reconciliation:** `main@c5cda2c9` (2026-07-21, `DOC-SNAPSHOT-RECONCILE-02`). At that commit — and only at that commit — *every* row was re-verified against live code by dedicated read-only passes: five drift lanes (recursive composition, composer slot-projection, textOverflow/RN IR-authority, native compile lanes + rail descriptors, iconography) plus a staleness audit of every pre-existing row.
2. **Targeted re-sweep:** `main@90804abc` (2026-08-17, `DOC-SNAPSHOT-RESWEEP-01`). All 33 rows were re-verified against live code — every cited path, count, and spec status re-derived. Result: **24 rows accurate as written, 9 drifted** — 6 stale counts and 3 under-claims. **Zero over-claims and zero broken evidence paths**: no row claimed more than the code supports, and every cited file, test, and spec resolved. The 9 were corrected in this pass.
3. **Rows amended since either sweep:** the ledger is edited continuously as slices close. Those rows carry their own evidence in-row (spec ids, merge shas, script names) and are not vouched for by this header.
4. **Targeted oracle/authorship reconciliation:** feature commit `3022618b` (2026-09-04, `FIX-A11Y-ORACLE-IDREF-01`). This was not another whole-ledger sweep. It re-derived the target-selection, runtime-preview, a11y-oracle, test-governance, and authorship-review claims amended below, and measured the initial curated contract-mutant catalog end to end.

**What the re-sweep learned about this ledger's failure mode.** Every defect was a *count* or an *omission*, never a false capability claim. The counts that rot are the ones restating a number a live source already derives — audit gap totals, corpus sizes, self-test tallies. Prefer citing the deriving source (`known-gaps.json`, the component-token audit output) over pasting its current value. Two under-claims were campaigns that finished without the row being updated, so the ledger sent readers to redo completed work — the inverse failure, and one a status-only reading of "closed specs" would have caught.

So: **trust a row's own cited evidence, not a blanket header claim.** If a row cites a spec id or merge sha, that is its provenance. If it cites neither, treat it as unverified until someone re-derives it. `git log -- docs/current-implementation-snapshot.md` shows when any given row last moved.

A re-sweep is due whenever the gap between (2) and HEAD stops being legible — at that point re-run the reconciliation and record it as a new numbered entry above, rather than editing an existing one.

Known surfaces still without a row: the visual-fidelity/token-enrichment campaign (its outcomes surface indirectly through the styling-realization audits row's gap counts) — recording it row-grade requires its own verification pass.

This document is not a replacement for the underlying architecture docs. It is an index of claim strength: what is implemented, what the evidence actually proves, what it does not prove, and which older docs should no longer be read as the only truth surface.

## Freshness rule

Use this order when answering "what is true now?":

1. Current implementation snapshot.
2. Code and workflow surfaces at the cited commit.
3. Implemented/proven docs with `verified_at_commit`.
4. Architecture and reference docs.
5. the machine-local successor ledger (`docs/internal/successor-work.md`, when present) only for remaining work, not as a statement that everything listed is unimplemented.

If an older doc says a surface is future work but this snapshot identifies an implemented surface, treat the older language as stale until that specific doc is reconciled.

## Resolved architectural finding: component CSS collision isolation (option a)

Research during `ICONOGRAPHY-TOKEN-DISCIPLINE-02` (Phase 5) recorded a real, unmitigated collision concern. Fix option (a) — `@layer` wrapping — shipped under `FEAT-BRAND-PERSONA-SCOPE-01` (closed, worktree-merge `8107091b`) and `FEAT-BRAND-PERSONA-VISUAL-QA-01` (closed, worktree-merge `3c5f398f`):

- **Component CSS is now layered.** `generateLayerDeclaration()` (`packages/ds-tokens/build/generators/global.ts:917`) declares a 6-layer order — `@layer core, semantic, components, theme, brand, density;` — and `emitTokensCss` (`packages/ds-codegen/src/css.ts:379`) wraps every generated component's structure/tokens CSS in `@layer components`. This closes the original gap: FSDS component rules are no longer unlayered.
- **Why this also fixes collision isolation, not just intra-FSDS overrides.** Per the CSS Cascade Layers spec, unlayered styles always win over layered styles regardless of specificity or layer order. Moving component CSS into `@layer components` means a consuming app's plain (unlayered) CSS now reliably beats FSDS's component CSS without `!important` or specificity tricks — the collision concern this section originally flagged.
- **What it unlocked inside FSDS:** `components.<Name>.<path>` brand overrides (`packages/ds-tokens/src/brands/_schema.json`, `components` property; implemented via `componentNameToKebab`/`componentTokenPathToCSSVar`/`walkComponentBrandSubtree`/`processComponentBrandTokens` in `packages/ds-tokens/build/generators/global.ts`) land in `@layer brand`, which is declared after `@layer components`, so a brand's component-scoped override now deterministically wins over that component's own default without needing to out-specificity it.
- **Non-claims, carried forward:** this closes fix option (a) only. Option (b) — prefixing every generated selector with `[data-fsds-component="<cssPrefix>"]` for per-component isolation granularity — remains undone; the identification attribute from Phase 5 is still identification-only and does not prefix any selector. The layer mechanism is a `<link>`/`<style>` document-level cascade feature — it does not reach Lit's shadow DOM (`emitLitInlineCss` renders inside a separate cascade context `@layer` cannot cross), so Lit's style isolation still comes from shadow DOM boundaries, not from this layer order.
